# Отчёт по заданию: Балансировка

## 1. Приложение и окружение

В локальном Kubernetes-кластере minikube с драйвером Docker работают две версии приложения. 
Версия встраивается при сборке образа аргументом `APP_VERSION` (см. [Dockerfile](Dockerfile)). 
Обработчик `GET /version` возвращает версию и имя pod в JSON, а middleware добавляет заголовки `X-App-Version` и `X-Pod-Name`.

| Версия | Образ | Deployment | Готовые реплики | Отдельный Service | Тип |
|---|---|---|---|---|---|
| v1 | `meeting-rooms:deploy-v1` | `rooms-stable` | 2/2 | `rooms-stable` | ClusterIP |
| v2 | `meeting-rooms:deploy-v2` | `rooms-green` | 2/2 | `rooms-green` | ClusterIP |

Namespace: `rooms-strategies`. 
Оба приложения используют общую PostgreSQL. 
HTTP-трафик принимает Envoy Gateway v1.10.0. GatewayClass `rooms-eg` связывает Gateway `rooms` с контроллером Envoy. 
HTTPRoute `rooms` направляет запросы к двум Service с весами 90 и 10. 
Число реплик одинаковое; доли трафика задаются весами HTTPRoute.

Цепочка запроса: клиент → локальный port-forward → Service прокси Envoy → Gateway/HTTPRoute → ClusterIP Service выбранной версии → pod Roomly.

### Контроллер, GatewayClass и Gateway

Файл - [deploy/gateway.yaml](deploy/gateway.yaml). Контроллер устанавливается Helm-командой из раздела 3; `EnvoyProxy` задаёт ClusterIP для его прокси.

```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: EnvoyProxy
metadata:
  name: rooms
  namespace: rooms-strategies
spec:
  provider:
    type: Kubernetes
    kubernetes:
      envoyService:
        type: ClusterIP
---
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: rooms-eg
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: rooms
  namespace: rooms-strategies
spec:
  gatewayClassName: rooms-eg
  listeners:
  - name: http
    protocol: HTTP
    port: 80
    allowedRoutes:
      namespaces:
        from: Same
  infrastructure:
    parametersRef:
      group: gateway.envoyproxy.io
      kind: EnvoyProxy
      name: rooms
```

### HTTPRoute с весами 90/10

Файл: [deploy/strategies/canary-90-10.yaml](deploy/strategies/canary-90-10.yaml).

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: rooms
  namespace: rooms-strategies
spec:
  parentRefs:
  - name: rooms
  rules:
  - backendRefs:
    - name: rooms-stable
      port: 8080
      weight: 90
    - name: rooms-green
      port: 8080
      weight: 10
```

## 3. Как воспроизвести

Необходимы работающий Docker, minikube, kubectl, Helm и Python 3. 

Команды выполняются из корня проекта, а скрипт установки запускает minikube, устанавливает Envoy Gateway, собирает образы с `APP_VERSION=v1` и `APP_VERSION=v2`, создаёт базу, выполняет миграции и разворачивает приложения:

```bash
bash scripts/deployment/setup.sh
kubectl --context minikube apply -f deploy/strategies/canary-90-10.yaml
kubectl --context minikube -n rooms-strategies wait --for=condition=Programmed gateway/rooms --timeout=180s
kubectl --context minikube -n rooms-strategies get deployments,services,gateway,httproute
kubectl --context minikube -n rooms-strategies get httproute rooms -o yaml
```

В статусе HTTPRoute нужно проверить `Accepted=True` и `ResolvedRefs=True`, а также соответствие `observedGeneration` текущему `metadata.generation`. В выполненной проверке оба условия подтверждены; у Gateway — `Programmed=True`.

В отдельном терминале открыть доступ к Service прокси Envoy:

```bash
DEMO_PORT=18888 bash scripts/deployment/forward.sh
```

После сообщения `Forwarding from 127.0.0.1:18888` выполнить проверку:

```bash
python3 scripts/deployment/check-traffic.py --url http://127.0.0.1:18888/version --count 200
```

Скрипт отправляет 200 последовательных GET-запросов через Gateway, определяет версию по `X-App-Version` и сохраняет HTTP-статус, версию, имя pod, тело ответа и ошибку каждого запроса в CSV. 

Ошибки учитываются отдельно; при их наличии скрипт завершается с ненулевым кодом. 

Повторный запуск обновляет файлы результатов; для отдельной серии можно указать `--output evidence/gateway-90-10-repeat`.

В текущем окружении minikube и приложения уже работали. Были повторно применены `deploy/apps.yaml`, `deploy/gateway.yaml` и маршрут 90/10, затем проведена новая серия запросов. Переустановка контроллера и пересборка образов для этой серии не требовались.

## 5. Вывод по дз

Две версии приложения работают в minikube, каждой соответствует отдельный ClusterIP Service. Gateway и HTTPRoute приняты контроллером, веса backend заданы как 90/10.

Из 200 запросов v1 обработала 178 (89%), v2 — 22 (11%). Отклонение от заданных долей составляет 1 процентный пункт для каждой версии, или 2 запроса от ожидаемых 180/20. 

Взвешенная балансировка задаёт вероятностное распределение, поэтому точное соотношение в небольшой выборке не гарантируется. 
Полученное распределение близко к 90/10 и согласуется с заданными весами; ошибок запросов нет.
