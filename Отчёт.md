# Отчёт по заданию. Стратегии развёртывания приложения

## 1. Подготовка приложения

Я подготовила приложение к запуску в нескольких репликах и собрала два Docker-образа:

- `meeting-rooms:deploy-v1` — исходная версия;
- `meeting-rooms:deploy-v2` — обновлённая версия.

Добавила передачу версии при сборке через аргумент `APP_VERSION`. Версия встраивается в исполняемый файл. Маршрут `GET /version` возвращает версию приложения и имя пода. Дополнительно HTTP-ответы содержат заголовки `X-App-Version` и `X-Pod-Name`, позволяющие определить, какая реплика обработала запрос. В структурированные логи я добавила версию, имя пода, метод, путь запроса и заголовки для сопоставления запросов.

### 2. Хранение состояния и репликация

Состояние приложения хранится вне подов приложения, в общей базе PostgreSQL: пользователи, сессии авторизации, переговорные комнаты и бронирования. Для PostgreSQL я настроила PersistentVolumeClaim `postgres-data` объёмом 1 GiB.

Я создала два Deployment — `rooms-stable` и `rooms-green`, по две реплики в каждом, оба используют общую БД, и для каждого Deployment я создала отдельный Service, через который Envoy Gateway направляет запросы в соответствующую версию.

Чтобы проверить работу общей сессии, я зарегистрировала пользователя и выполнила 80 запросов `GET /api/me` с одной cookie. Один и тот же пользователь успешно авторизован через четыре пода обеих версий. Это подтверждает, что сессия доступна независимо от выбранной реплики.

Материалы: [манифесты приложения](deploy/apps.yaml), [PostgreSQL и PVC](deploy/database.yaml), [лог проверки состояния](evidence/logs/state.log).

### 3. Пробы и завершение работы

 Проверки:

| Проверка | Маршрут | Назначение |
|---|---|---|
| Readiness | `GET /readyz` | Проверяет доступность PostgreSQL. При ошибке возвращает HTTP 503, чтобы неподготовленная реплика не получала трафик. |
| Liveness | `GET /healthz` | Проверяет работоспособность HTTP-сервера независимо от состояния БД. |
| Startup | `GET /healthz` | Даёт приложению время на запуск до применения liveness-пробы. |

Для корректного завершения работы я настроила обработку SIGTERM, остановку HTTP-сервера и `preStop` с задержкой 5 секунд. На завершение пода выделено 25 секунд.

Код: [backend/app.go](backend/app.go), [backend/deployment.go](backend/deployment.go), [backend/main.go](backend/main.go), [Dockerfile](Dockerfile).

## 4. Развёртывание локального стенда

Я развернула локальный кластер minikube с Docker-драйвером и установила Envoy Gateway версии `v1.10.0` в namespace `envoy-gateway-system`. Ресурсы приложения я разместила в namespace `rooms-strategies`.

Для маршрутизации я использовала ресурсы Gateway API:

- `GatewayClass rooms-eg` с контроллером Envoy Gateway;
- `Gateway rooms` с HTTP-listener на порту 80;
- `HTTPRoute rooms`, правила которого меняются в зависимости от стратегии.

Для доступа к Gateway с локального компьютера я настроила port-forward на `http://127.0.0.1:8888`.

После запуска я проверила состояние ресурсов: minikube — `Running`, оба Deployment приложения — по две готовые реплики. Для Gateway получен статус `Programmed=True`, для HTTPRoute — `Accepted=True` и `ResolvedRefs=True`. PVC PostgreSQL находился в состоянии `Bound`.

Файлы стенда: [deploy/gateway.yaml](deploy/gateway.yaml), [setup.sh](scripts/deployment/setup.sh), [forward.sh](scripts/deployment/forward.sh). Результаты проверки окружения: [review-environment.log](evidence/logs/review-environment.log).

## 5. Демонстрация стратегий обновления

Для повторяемого выполнения демонстраций я подготовила скрипт [scripts/deployment/demo.py](scripts/deployment/demo.py). Он применяет конфигурации, отправляет HTTP-запросы через Gateway, проверяет результаты и сохраняет логи.

### 5.1. Rolling — постепенное обновление

Для постепенного обновления я настроила в Deployment `rooms-stable` стратегию `Rolling Update`:

```yaml
replicas: 2
minReadySeconds: 8
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

Затем я обновила образ приложения командой:

```bash
kubectl -n rooms-strategies set image deployment/rooms-stable app=meeting-rooms:deploy-v2
```

Новые реплики запускались постепенно, а старые выводились из работы по мере готовности новых. Во время обновления я непрерывно отправляла запросы и фиксировала версию и имя пода в ответах.

В результате я получила:

- до обновления — 30 ответов версии v1;
- во время обновления — 50 ответов v1 и 31 ответ v2;
- после обновления — 40 ответов версии v2;
- ошибок запросов во время обновления — 0.

**Лог:** [evidence/logs/rolling.log](evidence/logs/rolling.log).  
**Видео:** [evidence/video/rolling.mov](evidence/video/rolling.mov).

### 5.2. Blue/Green — переключение и откат

Для Blue/Green я одновременно запустила две группы подов: blue — `rooms-stable` с v1 и green — `rooms-green` с v2. Затем переключила весь трафик на green одной заменой HTTPRoute. Для демонстрации отката я повторно применила маршрут на blue:

```bash
kubectl apply -f deploy/strategies/stable.yaml
kubectl apply -f deploy/strategies/green.yaml
kubectl apply -f deploy/strategies/stable.yaml
```

После применения каждого маршрута я отправила по 60 запросов:

| Этап | v1 | v2 |
|---|---:|---:|
| Исходный маршрут blue | 60 | 0 |
| Переключение на green | 0 | 60 |
| Откат на blue | 60 | 0 |

Таким образом, я продемонстрировала полное переключение на новую версию и откат на исходную. Обе группы подов оставались запущенными, поэтому для возврата на v1 не потребовалась повторная сборка или запуск приложения. Ответы я проверяла после применения конфигурации Gateway.

Манифесты: [stable.yaml](deploy/strategies/stable.yaml), [green.yaml](deploy/strategies/green.yaml).

**Лог:** [evidence/logs/blue-green.log](evidence/logs/blue-green.log).  
**Видео:** [evidence/video/blue-green.mov](evidence/video/blue-green.mov).

### 5.3. Canary — увеличение доли новой версии

Для Canary я настроила распределение запросов весами `backendRefs` в HTTPRoute. Я последовательно увеличивала долю новой версии: 90/10 → 50/50 → 0/100. На каждом этапе отправила по 1000 запросов.

| Этап, v1/v2 | Ответы v1 | Ответы v2 |
|---|---:|---:|
| 90/10 | 900 | 100 |
| 50/50 | 500 | 500 |
| 0/100 | 0 | 1000 |

В этом прогоне я получила распределение, соответствующее заданным долям. На последнем этапе все запросы обработала новая версия. При повторении эксперимента доли на промежуточных этапах могут отклоняться от весов из-за вероятностного распределения трафика.

Манифесты: [canary-90-10.yaml](deploy/strategies/canary-90-10.yaml), [canary-50-50.yaml](deploy/strategies/canary-50-50.yaml), [canary-0-100.yaml](deploy/strategies/canary-0-100.yaml).

### 5.4. A/B — выбор версии по аудитории

Для A/B я выделила тестовую аудиторию с помощью HTTP-заголовка `X-Audience: beta` и настроила правило его точного совпадения. Такие запросы направляются в `rooms-green` с версией v2. Остальные запросы поступают в `rooms-stable` с версией v1.

Я проверила три группы по 100 запросов:

| Аудитория | Результат |
|---|---|
| Без `X-Audience` | 100 ответов v1 |
| `X-Audience: beta` | 100 ответов v2 |
| `X-Audience: other` | 100 ответов v1 |

Новая версия доступна выбранной аудитории; маршрутизация остальных пользователей сохраняется на исходную версию.

Манифест: [ab.yaml](deploy/strategies/ab.yaml).

### 5.5. Shadow — зеркалирование трафика

Для Shadow я настроила в HTTPRoute фильтр `RequestMirror`: основной запрос `GET /version` направляется в `rooms-stable`, его копия — в `rooms-green`. Клиент получает ответ основной версии v1, ответ зеркальной версии v2 не используется.

Я отправила 20 запросов с уникальными значениями заголовка `X-Audience`, чтобы сопоставить исходные запросы и их копии. Затем сравнила логи обеих версий.

Результат:

- все 20 клиентских ответов получены от v1;
- в логах `rooms-stable` найдены все 20 идентификаторов;
- в логах `rooms-green` найдены те же 20 идентификаторов;
- подтверждена доставка копий запросов в новую версию.

Я ограничила зеркалирование диагностическим GET-маршрутом `/version`, чтобы демонстрация не приводила к повторному выполнению операций изменения данных.

Манифест: [shadow.yaml](deploy/strategies/shadow.yaml).

**Лог демонстрации:** [evidence/logs/shadow.log](evidence/logs/shadow.log).  
**Логи основной версии:** [evidence/logs/shadow-rooms-stable.log](evidence/logs/shadow-rooms-stable.log).
