# Отчёт по приложению Roomly

## Доменная область

Roomly — сервис бронирования переговорных комнат в офисе. Пользователь
регистрируется, входит в систему, управляет справочником комнат, создает
бронирования для рабочих встреч и может сменить пароль.

Основная бизнес-логика приложения: одну и ту же переговорную комнату нельзя
забронировать на пересекающиеся интервалы времени. Это защищает пользователей
от конфликтов расписания.

В системе есть две роли. Администратор управляет справочником комнат и всеми
бронированиями. Обычный пользователь может смотреть список комнат, создавать
свои бронирования и видеть только свои записи.

## Стек реализации

- Язык и бэкенд: Go, стандартная библиотека `net/http`.
- API: HTTP/REST поверх HTTP/1.1.
- Фронтенд: HTML, CSS, JavaScript без отдельного фреймворка.
- База данных: PostgreSQL.
- Драйвер PostgreSQL: `github.com/jackc/pgx/v5/stdlib`.
- Контейнеризация: Docker и Docker Compose.

## Архитектура приложения

Приложение реализовано в клиент-серверной архитектуре. Фронтенд обращается к
бэкенду через REST API, а бэкенд хранит состояние в PostgreSQL.

Бэкенд имеет простую слоистую структуру:

- `backend/main.go` — точка входа, чтение конфигурации, подключение к базе,
  запуск HTTP-сервера;
- `backend/app.go` — сборка HTTP-приложения и маршрутов;
- `backend/auth.go` — регистрация, вход, выход, смена пароля, сессии и роли;
- `backend/room.go` — операции с переговорными комнатами;
- `backend/booking.go` — операции с бронированиями и проверка пересечений;
- `backend/migrate.go` — применение SQL-миграций.

Фронтенд разделён на три части:

- `web/index.html` — разметка интерфейса;
- `web/styles.css` — стили;
- `web/app.js` — API-клиент, состояние страницы, рендер списков и обработчики
  пользовательских действий.

По смыслу фронтенд близок к простому MVC: HTML выступает как View, состояние и
рендер находятся в JavaScript, а REST API используется как источник модели
данных.

## Основные сущности

### User

Пользователь приложения.

Поля:

- `id` — уникальный идентификатор пользователя.
- `username` — логин пользователя.
- `password_hash` — хэш пароля.
- `role` — роль пользователя: `admin` или `user`.
- `created_at` — дата создания пользователя.

### Session

Сессия авторизованного пользователя.

Поля:

- `token` — случайный токен сессии.
- `user_id` — пользователь, которому принадлежит сессия.
- `expires_at` — время истечения сессии.
- `created_at` — дата создания сессии.

### Room

Переговорная комната.

Поля:

- `id` — уникальный идентификатор комнаты.
- `name` — название комнаты.
- `capacity` — вместимость в людях.
- `location` — расположение комнаты.

CRUD-операции:

- `GET /api/rooms` — чтение списка комнат.
- `POST /api/rooms` — создание комнаты.
- `PUT /api/rooms/{id}` — обновление комнаты.
- `DELETE /api/rooms/{id}` — удаление комнаты.

### Booking

Бронирование переговорной комнаты.

Поля:

- `id` — уникальный идентификатор бронирования.
- `room_id` — забронированная комната.
- `user_id` — пользователь, создавший бронирование.
- `purpose` — цель встречи.
- `starts_at` — дата и время начала.
- `ends_at` — дата и время окончания.
- `created_at` — дата создания записи.

CRUD-операции:

- `GET /api/bookings` — чтение списка бронирований.
- `POST /api/bookings` — создание бронирования.
- `PUT /api/bookings/{id}` — обновление бронирования.
- `DELETE /api/bookings/{id}` — удаление бронирования.

## Авторизация и пользователи

В приложении реализованы регистрация, вход по логину и паролю, выход и смена
пароля текущего пользователя. После успешного входа или регистрации сервер
создает сессию в PostgreSQL и отправляет клиенту `HttpOnly` cookie. Все
маршруты `/api/*`, кроме `/api/login` и `/api/register`, доступны только
авторизованному пользователю.

Права доступа:

- администратор может создавать, редактировать и удалять комнаты;
- администратор видит и изменяет все бронирования;
- обычный пользователь видит список комнат без прав изменения;
- обычный пользователь видит, создает, редактирует и удаляет только свои
  бронирования.

Для локальной проверки миграция создает демонстрационного пользователя:

```text
Логин: admin
Пароль: admin123
```

## Соответствие методологии 12 факторов

### 1. Codebase

Приложение хранится в одном репозитории и представляет один кодовый базис.
Окружения отличаются только конфигурацией, а не исходным кодом.

### 2. Dependencies

Зависимости Go явно объявлены в `go.mod` и зафиксированы в `go.sum`.
Приложение собирается в Docker-образе, поэтому не зависит от глобально
установленных библиотек на машине пользователя.

### 3. Config

Конфигурация вынесена в переменные окружения:

- `DATABASE_URL` — строка подключения к PostgreSQL.
- `PORT` — порт HTTP-сервера.
- `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` — параметры базы для
  Docker Compose.

Пример локальной конфигурации находится в `.env.example`. Демонстрационная
учетная запись создается миграцией только для удобной локальной проверки.

### 4. Backing Services

PostgreSQL рассматривается как подключаемый backing service. Приложение
получает адрес базы через `DATABASE_URL`, поэтому базу можно заменить на другой
экземпляр PostgreSQL без изменения исходного кода.

### 5. Build, Release, Run

Стадии разделены:

- Build: сборка бинарного файла в Dockerfile.
- Release: Docker Compose передает переменные окружения и подключает сервисы.
- Run: запуск контейнера приложения командой `./server`.

Миграция схемы выполняется отдельной командой `./server migrate`.
SQL-миграции разнесены по файлам в папке `migrations/` и применяются по
порядку имени файла.

### 6. Processes

Бэкенд является stateless-процессом. Состояние приложения, включая комнаты,
бронирования и сессии, хранится в PostgreSQL, а не в памяти процесса или
файловой системе контейнера.

### 7. Port Binding

Приложение само поднимает HTTP-сервер и слушает порт из переменной `PORT`.
В контейнере опубликован порт `8080`.

### 8. Concurrency

Приложение запускается как один независимый HTTP-процесс. Масштабирование
возможно горизонтально: можно запустить несколько экземпляров приложения,
подключенных к одной PostgreSQL-базе. Сессии и бизнес-данные не привязаны к
конкретному процессу.

### 9. Disposability

Приложение быстро стартует, проверяет подключение к базе при запуске и корректно
завершается по `SIGINT`/`SIGTERM` через graceful shutdown.

### 10. Dev/Prod Parity

Локальный запуск через Docker Compose использует те же основные компоненты, что
и production-подобное окружение: контейнер приложения и PostgreSQL. Различия
сводятся к значениям переменных окружения.

### 11. Logs

Приложение пишет логи в стандартный вывод. Это позволяет Docker, orchestrator
или внешней системе логирования собирать и обрабатывать поток логов.

### 12. Admin Processes

Административная операция миграции запускается отдельной командой:

```bash
./server migrate
```

В Docker Compose аналогичная команда может быть выполнена так:

```bash
docker compose run --rm app migrate
```

Миграция использует тот же код и ту же конфигурацию подключения к базе, что и
основное приложение.

## Вывод

Проект соответствует требованиям задания: реализованы фронтенд и бэкенд,
данные хранятся в PostgreSQL, есть регистрация, авторизация, смена пароля,
роли пользователей, CRUD-операции над комнатами и бронированиями, а архитектура
приложения приведена в соответствие с методологией 12 факторов.
